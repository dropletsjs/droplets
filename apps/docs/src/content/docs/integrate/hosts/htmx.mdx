How a static page embeds droplets with htmx: `hx-get` swaps each fragment in
from the browser, and `/index.js` makes it live.

## The pattern in htmx

```html
<!-- html/shop.html (trimmed) -->
<head>
  <meta name="htmx-config" content='{"selfRequestsOnly": false}'>
  <script src="/vendor/htmx.min.js"></script>
  <script type="module" src="http://localhost:8000/index.js"></script>
  <script type="module" src="/index.js"></script>
  <script src="/droplet-origins.js"></script>
</head>
<body hx-boost="true">
  …
  <section id="product" hx-boost="false"
           hx-get="/droplets/product-page?slug=clay-cylinder-mug"
           hx-trigger="load">
    <p>Loading the product…</p>
  </section>
</body>
```

```nginx
# nginx.conf
location ~ ^/(index\.js|env\.js|index\.css|droplets/|assets/|api/) {
  proxy_pass http://shop;
  proxy_set_header Cookie $shop_cookie;
  proxy_set_header x-droplet-location ${SHOP_PUBLIC_URL};
  proxy_set_header Forwarded "";
  proxy_set_header X-Forwarded-Host "";
  proxy_set_header X-Forwarded-Proto "";
  proxy_set_header X-Forwarded-Prefix "";
}
```

- When the page loads (`hx-trigger="load"`), htmx asks for
  `GET /droplets/product-page?slug=clay-cylinder-mug` from the browser and
  puts the answer inside the `<section>`, in place of its placeholder.
- The request is same-origin, through nginx: the browser sends its cookies
  and the page's URL as `Referer` itself, and nginx cuts the `Cookie` down
  to the shop's own `cart_id` and `shop_admin` (a `map`), adds
  `x-droplet-location` and clears `Forwarded` and `X-Forwarded-*`.
  `nginx.conf` is a template; the nginx image fills in `${SHOP_PUBLIC_URL}`
  (`http://localhost:8010`) when it starts.
- `/index.js`, loaded once, defines the shop's droplet element (`djs-shop`),
  so each fragment htmx swaps in upgrades and hydrates as it lands. nginx
  passes `/index.js`, `/env.js`, `/index.css`, `/droplets/*`, `/assets/*` and `/api/*` on to the shop.
- The `<body>` has `hx-boost="true"`, so each droplet's section has
  `hx-boost="false"` ([With `hx-boost`](#with-hx-boost)). The second
  `/index.js`, the `htmx-config` meta and `droplet-origins.js` are for the
  Svelte example's droplets, which come from another origin
  ([Cross-origin](#cross-origin)).

### Pieces and ports

`docker-compose.yml` starts three services:

| Service | Port | What it is |
| --- | --- | --- |
| `web` | 8010, on `127.0.0.1` | `nginx:1.27-alpine` serving the two pages and htmx, and proxying the shop under its own origin |
| `droplets` | 8000, on `127.0.0.1` | the Svelte example's droplets server: the browser asks it for fragments directly, cross-origin |
| `shop` | 8300, internal only | the shop's droplets server (`examples/shop`), behind `web` |

`/` embeds the Svelte example from its own origin, to show what a
cross-origin page needs. `/shop` embeds the shop through the proxy, so its
forms and cookies are the page's own; its cart badge is an element the page
writes itself, `<djs-shop data-droplet="shopping-cart" data-params='{"variant":"badge"}'>`,
which renders in the browser and fetches its own data.

htmx is the npm package `htmx.org` 2.0.11, pinned in `package.json` and
`package-lock.json`: the `Dockerfile` installs it with `npm ci --ignore-scripts`
and copies `dist/htmx.min.js` into the nginx image as `/vendor/htmx.min.js`.
No CDN is involved.

`nginx.conf` is a template (the nginx image's `/etc/nginx/templates/`):
`SHOP_PUBLIC_URL` (`http://localhost:8010`) and `DROPLETS_PUBLIC_URL`
(`http://localhost:8000`) are filled in at start. The pages are written for
the default ports; when the droplets server is published elsewhere
(`DROPLETS_PORT`, `DROPLETS_URL`), `sub_filter` rewrites
`http://localhost:8000` in them to `DROPLETS_PUBLIC_URL`.

Both droplets servers list `http://localhost:8010` in
`DROPLETS_TRUSTED_ORIGINS`. For the shop, it is the origin of the
`x-droplet-location` nginx sends and of the pages' form posts. For the
Svelte example, it is the page's `Origin`, which htmx's cross-origin
requests carry: the droplet's `host` is that origin, within the list.

### Run it

```bash
cd examples/hosts/htmx
docker compose up --build
open http://localhost:8010        # the Svelte droplets; /shop has the forms
```

`pnpm test:hosts htmx` runs it end to end (`tests/hosts/e2e/htmx.spec.ts`),
from the repository root; htmx runs only by name, not in the default set.
The test also checks that the Svelte example answers htmx's preflight with
`204`, `access-control-allow-origin: *` and the `HX-*` headers echoed.

## Swapping a droplet in

htmx is built around HTML fragments from a server, and a droplets server
serves exactly that: `GET /droplets/<id>` answers a droplet element with its
server-rendered markup. Load `/index.js` once and every droplet element on
the page comes alive, whether it was there at first or htmx swapped it in
later. Nothing renders the page on a server: it is a static file.

```html
<head>
  <script src="/vendor/htmx.min.js"></script>
  <script type="module" src="http://localhost:8000/index.js"></script>
</head>
<body>
  <section hx-get="http://localhost:8000/droplets/ssr-hydrate?who=htmx" hx-trigger="load">
    <p>Loading…</p>
  </section>
</body>
```

htmx asks for the fragment and puts it in the section (the default
`innerHTML` swap). The browser upgrades the element as soon as it is in
the document, since `/index.js` defined it, and the element does what it
does on any page:

- it links its stylesheet inside itself (the fragment's
  `<link data-droplet-style>`) and waits for it before it mounts, so the markup
  never shows unstyled;
- it hydrates as the droplet says: `ssr-hydrate` hydrates at once, `client`
  renders in the browser and fetches its data, `ssr-nohydrate` stays server
  HTML and loads no bundle, and the shop's `product-card` loads its bundle
  only when it is about to scroll into view (`hydrate = "visible"`);
- its JavaScript, CSS and data come from where `/index.js` came from, here
  the droplets server's own origin.

htmx leaves the fragment's `<script type="application/text">` tags alone:
it runs only JavaScript scripts in swapped content.

## When it loads: `hx-trigger`

The trigger decides when the fragment is asked for. The example uses three:

```html
<!-- As soon as the page loads. -->
<section hx-get="http://localhost:8000/droplets/ssr-hydrate?who=htmx" hx-trigger="load">…</section>

<!-- When asked: the fragment goes into #on-click. -->
<button hx-get="http://localhost:8000/droplets/client?who=Ana" hx-target="#on-click">Load the client droplet</button>
<div id="on-click"></div>

<!-- Only once it scrolls into view: nothing is requested before. -->
<section hx-get="http://localhost:8000/droplets/ssr-nohydrate?who=htmx" hx-trigger="revealed">…</section>
```

`revealed` delays the fragment itself: before the section is in view, no
request goes to the droplets server at all. It adds up with the droplet's
own [lazy hydration](/guides/in-the-browser/#lazy-hydration): the shop's
product card, swapped in on `revealed`, still loads its bundle only when
visible. The page's first paint has no droplet markup in it, which is the
price of composing in the browser; a page that needs the markup at once
pastes the fragment on its server (every other host on this list).

## Cross-origin

When the page and the droplets server are on different origins, two
things need saying, one to htmx and one to the droplets server.

**htmx.** htmx 2 only talks to the page's own origin by default
(`selfRequestsOnly`); a cross-origin `hx-get` is refused with an
`htmx:invalidPath` event and nothing is swapped. That check runs before
htmx fires `htmx:validateUrl`, so a listener alone cannot allow an origin:
turn it off in the page, and put the listener in its place, allowing the
droplets servers' origins and no other. The example reads them from the
`/index.js` scripts the page loads (`html/droplet-origins.js`, a file, so
a page with a Content-Security-Policy needs no inline script):

```html
<meta name="htmx-config" content='{"selfRequestsOnly": false}'>
<script src="/droplet-origins.js"></script>
```

```js
// html/droplet-origins.js
const origins = new Set(
  Array.from(document.querySelectorAll('script[type="module"][src]'))
    .map((script) => new URL(script.src))
    .filter((url) => url.pathname.endsWith("/index.js"))
    .map((url) => url.origin),
);

document.addEventListener("htmx:validateUrl", (event) => {
  const { url, sameHost } = event.detail;
  if (!sameHost && !origins.has(url.origin)) event.preventDefault();
});
```

A refused URL raises htmx's own `htmx:invalidPath`, and no request goes
out; the end-to-end test checks it with an `hx-get` to a third origin.

**The droplets server.** htmx sends its own headers (`HX-Request`,
`HX-Current-URL`, `HX-Target`, `HX-Trigger`), so the browser asks first,
with a preflight. [`cors`](/guides/security/#cors) answers it:
`cors: true` allows every origin and echoes the headers asked for, which is
also what lets the elements import their bundles cross-origin. The Svelte
example has it.

With only that, Chrome's console shows "Refused to get unsafe header
`HX-Trigger`" (and the other `HX-*` response headers) after each swap: htmx
reads them and CORS does not expose them. The swap works all the same. To
quiet it, expose them, and list your page's origin while you are at it:

```ts
// droplets.config.ts
export default config({
  cors: {
    origin: ["https://www.example.com"],
    exposeHeaders: [
      "HX-Trigger", "HX-Location", "HX-Refresh", "HX-Redirect", "HX-Push", "HX-Push-Url",
      "HX-Replace-Url", "HX-Retarget", "HX-Reswap", "HX-Reselect",
      "HX-Trigger-After-Swap", "HX-Trigger-After-Settle",
    ],
  },
});
```

This is not in the example, which keeps the Svelte example's `cors: true`.
`Link` and `x-droplets-build` stay exposed either way.

The cross-origin requests carry no cookies (htmx's `withCredentials` is off),
and their `Referer` is the page's origin alone. A droplet that needs the
visitor's cookies, or forms that come back by Post/Redirect/Get, are
simpler on the page's own origin: that is why `/shop` goes through the
proxy.

## Forms

The shop's droplets, swapped into `/shop` through the proxy, keep both
ways a droplet form works.

**Enhanced.** The product page is a Handlebars droplet with no JavaScript
of its own (`hydrate = false`), and its form has `data-droplets-enhance`
([enhancing a form](/guides/actions/#enhancing-a-form)), which the element
`/index.js` defined handles. The submit goes by `fetch` to `?/add` with
`accept: application/json`, without htmx's `HX-*` headers, and is answered
with the action's result as JSON. The element then asks for its fragment
again with that result as `form` and swaps it in place: no page load. The
cart badge hears of it (`droplets:action`) and counts the product. The
product card further down, swapped in on `revealed`, hydrates once visible
and enhances its form too.

**Plain (Post/Redirect/Get).** The login droplet ships no JavaScript and
never enhances its form: it is a native form. A wrong
password answers `303` back to `/shop` with the signed result in the query
(`__droplet_form_login_<build>=…`). The page loads again, htmx asks for the
login fragment on load, and the request's `Referer` is that URL, query
included; the shop's `handle` takes `host` from it
(`event.host = hostFrom(event.request.headers.get("referer")) ?? event.host`),
so the droplet renders with the result: "Wrong user or password." This
needs `DROPLETS_SECRET` on the droplets server and the page's origin in
`DROPLETS_TRUSTED_ORIGINS`, as for any host.

### With `hx-boost`

`hx-boost` on the `<body>` turns every link and form under it into an htmx
request, a droplet's forms included. htmx's listener is on the form, so it
runs before the droplet's: without an exclusion the enhanced form never
runs its own submit. htmx posts it as a plain form, follows the `303` and
swaps the whole `<body>` for the page it lands on, so every droplet on the
page is taken down and asked for again. Keep htmx out of the droplets with
`hx-boost="false"` on the element that receives them:

```html
<body hx-boost="true">
  <section hx-boost="false" hx-get="/droplets/product-page?slug=clay-cylinder-mug" hx-trigger="load">…</section>
  <section hx-boost="false" hx-get="/droplets/login?next=/shop" hx-trigger="load">…</section>
</body>
```

`hx-disable` is not the tool here: it stops htmx on the element itself as
well, so a container with `hx-disable` never asks for its fragment.

### Boosted navigation

A boosted link swaps only the `<body>`: the next page's `<head>` is not
loaded, so its scripts and its `htmx-config` never run. Give every page the
same `<head>`, with each droplets server's `/index.js` the site uses. The
example's two pages load both:

```html
<meta name="htmx-config" content='{"selfRequestsOnly": false}'>
<script src="/vendor/htmx.min.js"></script>
<script type="module" src="http://localhost:8000/index.js"></script>
<script type="module" src="/index.js"></script>
<script src="/droplet-origins.js"></script>
```

Back and forward work: htmx restores the page from its history and asks
for the fragments on `load` again, and each droplet renders and hydrates
once, as it did the first time. The end-to-end test goes back to `/shop`
this way and checks the product page is there once.

## Limits

- **No markup in the first paint.** The fragments arrive after htmx runs;
  without JavaScript the page shows its placeholders. Paste the fragment on
  a server for that ([Overview](/integrate/hosts/overview/)).
- **Props in the URL only.** `hx-get` sends props as the query string, as
  any `GET` fragment takes them. htmx can `POST`, but as a form body, which
  a droplets server treats as a [form action](/integrate/http-contract/#form-actions):
  a JSON render needs htmx's `json-enc` extension, not tried here.
- **The droplet element is the fragment's.** Its attributes
  (`data-hydrate` included) come from the server; the page sets them only on
  elements it writes itself.
- **Media.** The recording above is written by `pnpm test:hosts htmx --docs`.
