## Structure

One folder per droplet, under `dropletsFolder` (`src/droplets` by default):

```
src/droplets/<name>/
  +droplet.<ext>       # required: the component (.svelte, .vue, .tsx, .hbs…)
  +droplet.ts          # optional: load, props schema, handleError; server and browser
  +droplet.server.ts   # optional: load, handleError, entries, transform; server only
  +error.<ext>         # optional: the error page, in the same framework
```

Instead of a component, a droplet can be plain browser code: a
`+droplet.script.ts` (or `.js`), with the same loads. See
[Plain script](/renderers/script/).

`djs add <name>` writes one, asking for the framework, the target and the
optional files (see [`djs add`](/reference/api/#djs-add)).

The folder name becomes the route id, kebab-cased: `HelloWorld` is served
as `hello-world`. `+Droplet.vue` with a capital D also works. No id is
reserved; every droplet route lives under `/droplets/<id>`.

The component's extension picks the [renderer](/renderers/) that
builds it. One component per folder: a `+droplet.svelte` next to a
`+droplet.vue` is an error that says which one to keep.

Anything else in the folder, or anywhere in the project, is imported as
usual. A component shared by several droplets lives wherever you like; the
dev server tracks which droplets depend on it.

## Flags

Three flags decide how a droplet is delivered. Each renderer reads them from
where its components can export a constant: `<script module>` in Svelte, a
plain `<script>` in Vue, named exports in React, Preact, Solid, Hono JSX and Lit,
the opening comment (or `+droplet.ts`) in Handlebars. Each
[renderer's page](/renderers/) shows where.

```svelte
<script module lang="ts">
  export const ssr = true;        // false: nothing rendered on the server
  export const hydrate = true;    // false: no JavaScript; "visible" | "interactive": later
  export const prerender = false; // true: rendered at build for `entries`
</script>
```

| `ssr` | `hydrate` | Result |
| --- | --- | --- |
| `true` | `true` | Server-rendered, then hydrated. The default. |
| `true` | `false` | Server-rendered only. No bundle is built or served for it. |
| `false` | `true` | Client-only. The server load still runs and its data comes inline. |
| `true` | `"visible"` | Server-rendered; hydrates when it is about to scroll into view. |
| `true` | `"interactive"` | Server-rendered; hydrates on the first interaction with it. |

`"visible"` and `"interactive"` are [lazy hydration](/guides/in-the-browser/#lazy-hydration);
a host can also override `hydrate` per element with `data-hydrate`.

Side by side, with [prerendering](/guides/prerendering/): what the host page
receives in each mode, and when the droplet's JavaScript loads.

<RenderModes />

The flags must be literals. They are read with a text scan before anything
is compiled, because they decide *how* the droplet is built. A value that is
not a literal (`export const ssr = !dev`) logs a warning and is ignored.

**One set of flags per droplet.** `+error.*` is the droplet's error boundary
and follows the droplet's flags: it renders on the server when the droplet
does, hydrates when the droplet does and ships in the droplet's bundle. Flags
declared in the error page are ignored, with a warning in dev.

A droplet with `hydrate = false` is the cheapest thing you can ship: HTML and
CSS, nothing else. Its `<style>` is still extracted and served.

## The load chain

```
+droplet.ts          props   (a Standard Schema)    server, and browser when no server rendered
        ↓  validated props
+droplet.server.ts   load({ request, host, locals, platform, cookies, setHeaders, droplet, props })   server only
        ↓  the result is inlined into the fragment
+droplet.ts          load({ host, props, data })     server and browser
        ↓  the result is the component's `data`
+droplet.<ext>       data
```

The **server load** in `+droplet.server.ts` runs once per request, on the
server. Its result is inlined into the fragment, so hydration needs no second
round trip. Read secrets, databases, `locals` and
[`cookies`](/guides/server/#cookies) here; cookies are read only in a load.

```ts
// src/droplets/hello/+droplet.server.ts
import { error, type LoadEvent } from "$droplets/server";

export const load = async ({ props, locals }: LoadEvent) => {
  const who = typeof props.who === "string" ? props.who : "world";
  if (who.length > 40) error(404, "Nobody with a name that long lives here.");
  return { who, requestId: locals.requestId };
};
```

The **universal load** in `+droplet.ts` runs after it: on the server while
rendering, and again in the browser before hydrating or mounting. It receives
`{ host, props, data }`, where `data` is what the server load returned
(`undefined` without one), and shapes it into the component's `data`.

```ts
// src/droplets/hello/+droplet.ts
import type { load as serverLoad } from "./+droplet.server.ts";

type ServerData = Awaited<ReturnType<typeof serverLoad>>;

export const load = ({ data }: { data: ServerData }) => ({
  ...data,
  greeting: `Hello ${data.who}!`,
});
```

Keep it pure: it has to produce the same result on both sides, or the
hydrated markup will not match what the server rendered.

Both files are optional. With neither, `data` is `undefined` and the component
simply renders. Both return a plain object, or nothing. A `Response` (from
`json()`, say) is refused: responses belong in [`+server.ts`](/guides/server/#api-routes).

`error(status, message)` and `redirect(status, location)` from
`$droplets/server` stop a server load and answer as an endpoint would: the
fragment responds with that status, no component renders. Anything else a
load throws goes to the [error page](/guides/errors/).

### `host`

`host` in load events is where the droplet renders: the host page, as a
`URL`. Where the droplet itself lives is its
[location](/integrate/http-contract/#x-droplet-location-the-public-location)
(`x-droplet-location` on the server, the URL `/index.js` came from in the
browser, `droplet.url()` from `$droplets/drop`); the fragment's own URL is
`request.url`.

On the server, first match wins:

1. `host` in a render request's JSON body: `{ "host": "https://shop.example/product/mug", "props": { … } }`;
2. `Origin`;
3. the origin of the droplets server's location.

Only `http:` and `https:` URLs count; a value that is not one is skipped for
the next source. With `trustedOrigins` set, a host outside it (and not this
server) becomes the location's origin. `Origin` carries an origin only, so
the path is `/` unless the body gave one.
`handle` in `src/hooks.server.ts` sees it first and may replace it; loads,
`transform` and the context sent to the browser get what `handle` left. A
host that sends its page as `Referer` (or `X-Forwarded-Uri`) gets the path too:

```ts
// src/hooks.server.ts
import { hostFrom, type Handle } from "$droplets/server";

export const handle: Handle = ({ event, resolve }) => {
  event.host = hostFrom(event.request.headers.get("referer")) ?? event.host;
  return resolve(event);
};
```

`hostFrom` checks a candidate the way the default is checked: an `http:` or
`https:` URL without credentials or hash, and, with `trustedOrigins` set, one
of them or this server. Anything else, a missing or malformed header
included, gives `null`. `handle` may still set any `URL` it likes; `hostFrom`
is the safe way to take one from a request.

`host` comes from the request: any client can send any value. Render with
it; never decide from it who may see what. Embedding a droplet also tells
its server the page's URL; see [Who sees what](/guides/security/#who-sees-what).

In the browser, the universal load's `host` is the page itself
(`window.location`, without its `#hash`), read when the droplet mounts. It does not follow a
single-page app's navigation afterwards. A universal load that renders from
`host.pathname` hydrates cleanly only when the server got the same path.

While prerendering, see [`host` at build](/guides/prerendering/#host-at-build).

### `setHeaders`

`setHeaders` in a server load sets headers on the droplet's answers: the
fragment and `_data`. Fragments are sent `cache-control: private, no-store`
unless the load says otherwise, so a droplet that is the same for everyone
opens itself to caches here:

```ts
// src/droplets/products/+droplet.server.ts
import type { LoadEvent } from "$droplets/server";

export const load = async ({ props, setHeaders }: LoadEvent) => {
  setHeaders({ "cache-control": "public, max-age=60" });
  return { products: await db.products(props.category) };
};
```

As in SvelteKit, each header can be set once (`setHeaders` throws on the
second), names and values are plain strings without line breaks, and
`set-cookie` is refused: cookies are set in `handle`, `+server.ts` or an
[action](/guides/actions/). The
headers go out when the droplet renders or loads; an error answer, or a load
that failed and shows its error page, carries none of them. A prerendered
render keeps the headers its load set at build and is served with them.
`handle` sees the response after and may change any of them. A `vary` the
load sets is kept, and the [host headers](/guides/security/#caching) are
added to it. `transform` and the universal load have no `setHeaders`.

## Props

Props are how a caller parameterises a droplet. They arrive, in precedence
order, from:

1. **A POST body**: `{ "props": { … } }` as JSON, or `{ "host": "…", "props": { … } }`
   to also say where the droplet renders.
2. **The query string**: `/droplets/hello?who=Ana` gives `props.who === "Ana"`.
   Every value is a string.
3. **The `x-droplet-props` header**: base64-encoded JSON, for props too large
   or too structured for a URL.

Props are client input, as `host` is: anyone can send any props. Check them
(a [schema](#a-props-schema)) and never trust them for access; see
[Security model](/guides/security/#request-input).

`c`, `t`, `__cb`, `noSSR`, `clientOnly` and `__droplet_return` are reserved
query keys, as are a key that starts with `/` (an action's name, `?/add`) and
any `__droplet_form_*` key: they never become props. The component itself
never receives props: they reach it through a load.

### A props schema

`export const props` in `+droplet.ts` validates them with any
[Standard Schema](https://standardschema.dev) library (zod, valibot, arktype…).
It runs before every load: on the server before `+droplet.server.ts`, in the
browser when no server rendered the droplet. Its output replaces the props, so
`?page=2` from a URL and `{ page: 2 }` from a POST body meet as the same
value. Props it refuses answer `400` before any load runs.

```ts
// src/droplets/article/+droplet.ts
import * as z from "zod/mini";

export const props = z.object({
  page: z._default(z.coerce.number().check(z.int(), z.positive()), 1),
});
```

The schema may be async: it can ask a server whether page 2 exists before
anything renders.

The library is yours: droplets calls the schema's `~standard.validate` and
nothing else, and ships none of its own. A droplet that loads in the browser
carries its schema there, so its size counts. The same `page` in two other
libraries, each giving `{ page: number }` to the load and to `./$types`:

```ts
// valibot
import * as v from "valibot";

export const props = v.object({
  page: v.optional(v.pipe(v.unknown(), v.transform(Number), v.integer(), v.minValue(1)), 1),
});
```

```ts
// arktype
import { type } from "arktype";

export const props = type({
  page: type("string.integer.parse | number.integer").pipe(type("number >= 1")).default(1),
});
```

#### JSON Schema

A JSON Schema describes props without checking them; a validator does that.
Wrapped once as a Standard Schema, it works like the others:

```ts
// src/lib/json-schema.ts
import { Validator } from "@cfworker/json-schema";
import type { FromSchema, JSONSchema } from "json-schema-to-ts";

// The validator applies no `default`, so a defaulted property stays optional.
type Output<S extends JSONSchema> = FromSchema<S, { keepDefaultedPropertiesOptional: true }>;

/** Errors that only point at a nested one. */
const SUMMARIES = new Set(["properties", "false"]);

/** A JSON Schema as a Standard Schema, the shape `props` in +droplet.ts takes. */
export function jsonSchema<const S extends JSONSchema>(schema: S) {
  const validator = new Validator(schema as object, "2020-12");
  return {
    "~standard": {
      version: 1 as const,
      vendor: "json-schema",
      validate(value: unknown) {
        const { valid, errors } = validator.validate(value);
        if (valid) return { value: value as Output<S> };
        return {
          issues: errors.filter((e) => !SUMMARIES.has(e.keyword)).map((e) => ({
            message: e.error,
            path: e.instanceLocation.split("/").slice(1),
          })),
        };
      },
      types: undefined as unknown as { input: unknown; output: Output<S> },
    },
  };
}
```

```ts
// src/droplets/article/+droplet.ts
import { jsonSchema } from "../../lib/json-schema.ts";

export const props = jsonSchema({
  type: "object",
  properties: { page: { type: "integer", minimum: 1 } },
  additionalProperties: false,
});
```

`json-schema-to-ts` gives `./$types` the props' type (`{ page?: number }`
here). `@cfworker/json-schema` runs without `eval`, so it works on Workers and
under a strict Content Security Policy; `ajv` compiles schemas with
`new Function` and does not.

A JSON Schema checks values; it does not convert them. `?page=2` arrives as
the string `"2"` and fails `type: "integer"`, and no `default` is filled in.
It fits props that callers send as JSON: a POST body or `x-droplet-props`.

## Types: `./$types`

Every droplet gets a generated `./$types`, typed from its own files. Its
component never repeats what the server load returns:

```ts
// src/droplets/article/+droplet.server.ts
import type { LoadEvent } from "./$types";

// `props.page` is a number: the schema in +droplet.ts says so.
export const load = async ({ props }: LoadEvent) => ({ page: props.page, items: await list(props.page) });
```

```svelte
<!-- src/droplets/article/+droplet.svelte -->
<script lang="ts">
  import type { DropletProps } from "./$types";

  let { data }: DropletProps = $props(); // { page: number; items: … }
</script>
```

| Type | What it is |
| --- | --- |
| `Props` | The caller's props after the `props` schema; `Record<string, unknown>` without one. |
| `LoadEvent`, `ServerLoad` | `load` in `+droplet.server.ts`, with `Props`. |
| `ServerData` | What that load returns; `undefined` without one. |
| `DropletLoadEvent`, `Load` | `load` in `+droplet.ts`: `Props` and `ServerData`. |
| `Data` | What the component gets: the `+droplet.ts` load's result, else `ServerData`. |
| `DropletProps` | The component's props, with the framework's `children` and `form`. |
| `ActionEvent`, `Actions` | `actions` in `+droplet.server.ts`, with `Props` (`satisfies Actions`). |
| `DropletActions` | Each action by name, with what `form` gets after it (its result or `fail()` data); `{}` without actions. For `actionUrl<DropletActions>()` and the enhance options. |
| `ActionData` | What `form` can be: each action's result or `fail()` data, or `undefined`; just `undefined` without actions. |
| `ErrorData`, `DropletErrorProps` | The error page's: what `handleError` returns. |
| `DropletScript` | A [script droplet](/renderers/script/)'s default export: `(data: Data, el: HTMLElement) => void \| (() => void)`. Only in script droplets' `./$types`. |

Annotate a load's parameter (`({ props }: LoadEvent) => …`) or use
`satisfies ServerLoad`, never `const load: ServerLoad`: an annotation would
replace the return type the component's `Data` is read from. The same goes
for `handleError` (`satisfies HandleDropletError`).

The files live in `.droplets/types/`, mirroring the droplet folders, and
`.droplets/tsconfig.json` maps them next to the droplets with `rootDirs`:
extend it from your `tsconfig.json`. `vite dev` rewrites them as droplets
come and go, `vite build` writes them too, and `djs sync` writes them without
either, for a type check on a fresh checkout (`"prepare": "djs sync"`).

Outside a droplet folder (a shared component, say), or before the project
has `./$types`, each renderer exports the generic form, which you fill in by
hand: `DropletProps<Data, Form>` from `@dropletsjs/renderer-svelte` (and the
other renderers), and `LoadEvent` from `$droplets/server`:

```ts
import type { DropletProps } from "@dropletsjs/renderer-svelte";

type Props = DropletProps<{ who: string }>;
```

Every example in these docs uses `./$types`.

## Data may be a promise

A load may return a promise, or an object whose fields are promises:

```ts
export const load = ({ props }: LoadEvent) => ({
  user: db.user(props.id),          // a promise
  posts: db.posts(props.id),        // another one
});
```

On the server, and when the browser hydrates, those fields are settled before
rendering: the component gets plain values, and the inline payload and `_data`
carry them settled. A field that rejects fails the load with that error, so
`error()` and `redirect()` inside a field still count.

A droplet mounted in the browser **from scratch** (client-only, no server
markup, a dev remount) mounts at once with `data` as a promise of what `_data`
and `+droplet.ts` answer. Read it the framework's way; the
[renderer pages](/renderers/) have the pattern for each one. Svelte
without `experimental.async` and Handlebars wait for the data instead, so
`data.x` works everywhere.

## Children

A droplet can render content the host puts inside it. Each renderer hands the
component a `children` value; where it renders, the host's content appears:

```svelte
<script lang="ts">
  import type { DropletProps } from "./$types";
  let { data, children }: DropletProps = $props();
</script>

<section>
  <h2>{data.title}</h2>
  {@render children?.()}
</section>
```

The host writes its content in one `<div data-droplet-slot>` inside the element;
see [Host children](/guides/in-the-browser/#host-children) for the browser
side and the rules.

## Styles

A droplet's stylesheets come in two kinds:

- **the shared stylesheet**, `css.path` in the plugin options (default
  `./src/app.css`), the same for every droplet: Tailwind, fonts, base styles;
- **its own**: `<style>` blocks, CSS a component imports, CSS modules. A
  component several droplets share gets a stylesheet of its own, which they
  all list.

**Styles belong to the component**: `+droplet.<ext>`, `+error.<ext>`, the
modules they import, or a `<style>` block. CSS reached from `+droplet.ts` or
`+droplet.server.ts`, directly or through what they import, fails
`vite build` and shows as an error in `vite dev`, with the import chain.
CSS imported as a string (`?url`, `?raw`, `?inline`) is not a stylesheet and
is fine anywhere.

`/droplets/<id>/style.css` imports both, the shared one first, and is linked
inside the element, never in the host's `<head>` (see
[the fragment](/integrate/http-contract/#the-fragment)). The browser downloads
each file once, whatever the number of droplets that list it.

**Every stylesheet lands in pages you do not control.** To keep them from
restyling the host, the framework confines them to the droplet element
(`css.scoped`, on by default): a PostCSS plugin rewrites every selector so it
only matches inside the element. That covers the shared stylesheet, CSS a
component imports, CSS modules, and Svelte and Vue component styles.

| You write | The host page gets |
| --- | --- |
| `.p-4 { … }` | `acme-widgets .p-4 { … }` |
| `*, ::before, ::after { … }` | `acme-widgets *, acme-widgets ::before, … { … }` |
| `:root { … }`, `html { … }`, `body { … }`, `:host { … }` | `acme-widgets { … }` |
| `@keyframes`, `@font-face`, `@property` | unchanged (nothing to scope) |

Svelte sees its `<style>` blocks before it compiles them, and drops a
selector naming an element its template lacks; there the prefix is written
`:global(acme-widgets)`, which Svelte leaves alone. A Svelte
`:global(body) .x` becomes `acme-widgets .x` like any `body .x`.

### Tailwind

Turn it on with `css: { tailwind: true }` and install `tailwindcss` and
`@tailwindcss/vite`. With scoping, `@import "tailwindcss"` is the right thing
to write: its preflight reset becomes the droplets' own reset, its theme
variables sit on the element and inherit into the droplet, and its utilities
only apply inside. `:root` is a handy way to style the element itself:

```css
/* src/app.css */
@import "tailwindcss";

@layer base {
  :root {
    display: block;
    font-family: ui-sans-serif, system-ui, sans-serif;
  }
}
```

When the host pages load Tailwind's preflight themselves, leave the
droplets' out of the build with `twPreflight`; see
[Preflight in dev only](/guides/configuration/#preflight-in-dev-only).

Tailwind generates one stylesheet per droplets server, from the classes all
its droplets use. Two droplets servers on one page each bring their own:
their utilities are scoped to their own element, so they do not collide, but
nothing is shared between them.

### Notes

Scoping does not rename `@keyframes` or `@font-face` names, which stay
global.

The plugin is added to Vite's `css.postcss` automatically. If your
`vite.config.ts` points `css.postcss` at a config file, add it there yourself:

```js
// postcss.config.js
import { scopeStylesPlugin } from "@dropletsjs/droplets/postcss";
export default { plugins: [scopeStylesPlugin({ element: "acme-widgets" })] };
```

With `css.scoped: false` nothing is rewritten; keep every stylesheet free of
resets and element selectors then, since they apply to the whole host page.

## Script droplets

Some droplets are no component at all: an analytics tracker, a third-party
widget, a vanilla UI. A **script droplet** is a `+droplet.script.ts` (or
`.js`) whose default export runs in the browser with the droplet's data and
its element, `(data, el) => void | cleanup`, with the same loads as any
droplet. The server renders nothing for it, `hydrate` is `true` or
`"visible"`, and no renderer is needed: it is built in.
[Plain script](/renderers/script/) has the details, a live one and an
example.

## Calling your API

A droplet runs inside someone else's page, so a relative `fetch("/api/…")`
reaches the host, not your droplets server. `$droplets/drop` knows the
droplets server's public origin, in the browser and during server rendering:

```ts
// src/lib/api.ts: neutral, any droplet in any framework can import it
import droplet from "$droplets/drop";

export async function bumpCounter(by = 1): Promise<number> {
  const response = await fetch(droplet.url("/api/counter"), {
    method: "POST",
    body: JSON.stringify({ by }),
  });
  return (await response.json()).count;
}
```

Cross-origin calls need `cors` on the droplets server, as the bundles do. A
host that proxies the droplets server under its own origin proxies `/api/*`
too. See [`$droplets/drop`](/reference/api/#dropletsdrop).

## Where code runs

Every file sits on one side of a line the build enforces. Server code stays
on the droplets server; the browser gets the component and what a load
returned, never the code that produced it:

<RunsWhere />

`$droplets/env` exports three booleans, usable anywhere:

| Export | `true` when |
| --- | --- |
| `browser` | running in the browser |
| `dev` | running under `vite dev` |
| `building` | `vite build` is prerendering |

Server-only modules (`$droplets/server`, `$droplets/env/private`) can only be
imported by server files: names with `.server.` in them, any extension
(`+droplet.server.ts`, `hooks.server.ts`, `db.server.tsx`…), `+server.*`
routes, or files under a folder named `server/`. Any other file that imports them fails the
build, and server files themselves never reach a browser bundle. See
[Environment variables](/guides/server/#environment-variables) and
[Server-only code](/guides/security/#server-only-code).
