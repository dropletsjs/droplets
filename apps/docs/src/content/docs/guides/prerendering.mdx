`export const prerender = true` renders the droplet at build time, once for
each event `entries` in `+droplet.server.ts` returns (`[{}]` without it). An
event is what the loads run with: `props`, and optionally `host`. An entry
may also name a `file`, to write its render as a
[static file](#static-files).

```ts
// src/droplets/docs/+droplet.server.ts
import type { Entries } from "$droplets/server";

export const entries = (() => [
  { props: { page: 1 } },
  { props: { page: 2 } },
  { props: { page: 3 }, host: "https://shop.example/docs" },
]) satisfies Entries;
```

## Where the renders live

- **With the server.** Renders are read per request: from
  `dist/server/_prerendered/` on Node, Bun and Deno; on Workers through the
  assets binding, from a directory of `dist/client` named anew every build
  that only the Worker knows. Nothing is bundled. An entry with a `file` is
  also written as a public file ([Static files](#static-files)).
- **Listed props are served from the store** (and `_data` answers from
  it). Other props render live, or answer `404` when `ssr = false`. A
  render made for a host page serves that page only (origin and path,
  never the query); see below.
- **A failed load is stored too**: a prop set whose load fails is stored as
  its error page, served with a `500`. One that answers `error()` or
  `redirect()` warns at build and renders live.
- **Renders go through `handle`**, with `building` from `$droplets/env` set
  to `true`.
- **`vite dev` renders everything live**, and ignores the configured
  `host`: an entry without its own `host` is host-agnostic there.

## Static files

An entry with a `file` is also written as a static file, which a CDN or the
platform's static files serve without the server:

```ts
// src/droplets/testimonials/+droplet.server.ts
import type { Entries } from "$droplets/server";

export const entries = (() =>
  Array.from({ length: 10 }, (_, i) => ({ props: { page: i + 1 }, file: `page-${i + 1}` }))) satisfies Entries;
```

- **Only with [`location` and `host` both set](/guides/configuration/#both-fixed)**
  in `droplets.config.ts`. Then a render holds no token and is the same for
  every request on `host`. Without both, `vite build` writes no file, serves
  these renders from the server as before, and warns once:

  ```
  prerender entries name files (testimonials/page-1, testimonials/page-2, …), but files are written only with both location and host set in droplets.config.ts (host is not set); no file is written, and these renders are served by the server as before
  ```
- **Where.** The file is `dist/client/assets/prerendered/<id>/<file>.html`,
  served at `<location>/assets/prerendered/<id>/<file>`, without `.html`
  (`https://cdn.example/mfe/assets/prerendered/testimonials/page-2`). Each
  build writes the folder anew.
- **What.** Exactly the fragment the server answers for those props on
  `host`'s root page, or on the entry's own `host` page: the element, the
  server HTML after `transform`, the payloads and the stylesheet link. A
  host embeds it as it embeds a fragment, and `/index.js` hydrates it the
  same way.
- **The name.** `file` is lowercase kebab-case (`page-2`: letters, digits,
  single hyphens), unique among the droplet's entries; the folder is the
  droplet's id. Another name, or one two entries share, fails the build,
  with or without `location` and `host`:

  ```
  droplets: testimonials: an entry's file is a lowercase kebab-case name such as "page-2" (letters, digits, single hyphens), got "Page 2"
  droplets: testimonials: two entries name the file "page-2"; give each entry its own file
  ```
- **Only what rendered.** A render that fails at build (its `+error` page),
  `error()` and `redirect()` write no file, and the build warns.

A file is answered without the server, so it has none of what the server
adds per request:

- no `handle`, no cookies and no `transform` per request. At build, the
  file goes through `handle` twice (the stored render, then the file) and
  `transform` once, with `building` true and no cookies;
- no headers from the load's `setHeaders` (the build warns), and no `Link`
  preload header;
- no form results: a form posted without JavaScript returns to `host`'s
  page, and its result renders live at `/droplets/<id>`, never from the
  file.

### Headers

The files' headers are those of every
[build file](/guides/deployment/#static-files-and-_headers), on every
adapter:

- `Cache-Control` is [`fragmentCacheControl`](/guides/configuration/#options)
  with `no-transform` added, as on every live fragment: by default
  `private, no-store, no-transform`, and `no-transform` alone for `false`;
- `Access-Control-Allow-Origin: *` and `X-Content-Type-Options: nosniff`,
  whatever `cors` says;
- an `ETag`, and `304` when `If-None-Match` matches. A file keeps its name
  from build to build, so it is never `immutable`.

On Cloudflare the rule is in the generated `dist/client/_headers`:

```
/assets/prerendered/*
  ! Cache-Control
  Cache-Control: private, no-store, no-transform
```

To give the files another `Cache-Control` there, put your own rule in the
`_headers` of the project root, which `vite build` appends after the
adapter's, starting with `! Cache-Control` so Cloudflare does not join the
two values:

```
/assets/prerendered/*
  ! Cache-Control
  Cache-Control: public, max-age=300
```

Without `no-transform`, Cloudflare may also compress the files, and inject
what the zone adds to HTML (analytics, Rocket Loader) into them.

### Serving them

- **Node, Bun and Deno** serve `/assets/prerendered/<id>/<file>` from
  `<file>.html`, and `<file>.html` too, never through `handle`.
- **Cloudflare Workers.** Static Assets serve the files before the Worker:
  no invocation. The extensionless URL depends on
  [`assets.html_handling`](https://developers.cloudflare.com/workers/static-assets/routing/advanced/html-handling/):
  keep the default (`auto-trailing-slash`, or `drop-trailing-slash`), which
  serves `<file>` from `<file>.html` and answers `<file>.html` with a `307`
  to `<file>`, its `Location` root-relative (a proxy in front that adds a
  prefix would lose it there: link the extensionless URL). A file named
  `index` is served at `<id>/`, and `<id>/index` redirects there, so give it
  another name. With `"none"` only `<file>.html` is served, and with
  `"force-trailing-slash"` `<file>` redirects to `<file>/`; the adapter warns
  once for either, when the build wrote files.
- **Elsewhere** (a CDN, nginx in front of `dist/client`), serve
  `dist/client/assets/` as files and map the extensionless URL to the
  `.html` file, e.g. `try_files $uri $uri.html =404;` under
  `location /assets/prerendered/`.

### In `vite dev`

`vite dev` checks every `file` and writes none. A request to
`/assets/prerendered/<id>/<file>` answers `404` with a plain text, and the
terminal warns once per path: the files are written by `vite build` only,
with `location` and `host` set. Under `vite dev`, ask for the live fragment
`/droplets/<id>` with the entry's props; to test the files, run `vite build`
and `vite preview`. With `location` set, the URLs inside a file point at
that location, not at the preview server.

## `host` at build

A render made at build has no request, so it may not know the page it will
be shown on. The rule: **in a host-agnostic render, read only
`host.origin`, `host.pathname` and `host.href`** (or `String(host)`). They
are filled in with each request's page; anything else stops the build.

```ts
// src/droplets/banner/+droplet.server.ts
import type { LoadEvent } from "./$types";

export const load = ({ host }: LoadEvent) => ({
  sale: `${host.origin}/sale`, // fine: filled in per request
  // host.searchParams.get("ref") would stop the build
});
```

Each entry renders for the first host page it can have:

1. the entry's `host`;
2. [`host`](/guides/configuration/#a-fixed-host) in `droplets.config.ts` (`host: "https://shop.example"`);
3. none: the render is **host-agnostic**.

An entry's `host` passes the same bound as a request's host page, or
`vite build` fails, naming the entry and the bound: with
[`host`](/guides/configuration/#a-fixed-host) in `droplets.config.ts` it is
on that origin (any page of it); without it, with
[`trustedOrigins`](/guides/configuration/#trusted-origins) or
`DROPLETS_TRUSTED_ORIGINS` (read from the build's environment) set, its
origin is listed (`"*"` lists every origin) or is the origin of
[`location`](/guides/configuration/#a-fixed-location); with neither, any
origin passes. A render for a host the server never gives the droplet would
never be served.

- **For the entry's `host`**, the loads get a real `URL`, and the render is
  stored under its props and that page's origin and path. A request gets it
  only when its own `host` matches.
- **For the configured `host`**, the loads get a real `URL` of that origin:
  `host.hostname`, `host.protocol` and `host.port` read as they are, and
  `host.search` and `host.hash` are empty. Its page is not known at build,
  so `host.pathname` and `host.href` are filled in with each request's
  page. It is stored under its props and the origin alone, and serves every
  page of that origin.
- **With [`location`](/guides/configuration/#both-fixed) set too**, a
  render for the configured `host` holds nothing to fill in:
  `host.pathname` is `/`, `host.href` is the origin's root, and the render
  is served exactly as stored.

A request looks for the render made for its page, then the one for the
configured `host`, then the host-agnostic one of the same props; with none,
it renders live.

When a render reads another field of a host-agnostic `host`
(`host.searchParams`, `host.hostname`, …), the build stops, even when the
droplet's code catches the error: the render answers `500` with
`x-droplets-prerender-error: host`, and `vite build` fails with
`HostUrlPropsErrorInPrerender`'s message. Give that entry a `host`, set
`host` in `droplets.config.ts`, or render it live.
[`cookies`](/guides/server/#cookies) stop the build the same way: there is
no request at build.

### How the values are filled in

- **Tokens.** In a host-agnostic render, `host.origin`, `host.pathname` and
  `host.href` (and `String(host)`, `JSON.stringify`) give the tokens
  `__$DROPLET_HOST$__` and `__$DROPLET_PATH$__`. Without `location` in the
  config, every render made at build also holds the droplet location as
  `http://droplets.invalid/__$DROPLET_LOCATION$__` (`droplet.origin`,
  action URLs, imported files). Each token carries the build's nonce
  (`__$DROPLET_HOST_<nonce>$__`), so content cannot fake one.
- **Per request.** The banner's `sale` above is stored as
  `__$DROPLET_HOST$__/sale`, in its markup and its inline data. Every request that serves it gets
  the tokens replaced with its own `host` and location, after `handle` and
  before `transform`: in the HTML (escaped for attributes), in the inline
  data, and in their `encodeURIComponent` forms.
- **Text and attributes only.** The values are HTML-escaped. Inside an
  inline `<script>` or `<style>` they get HTML escaping, not JavaScript or
  CSS escaping, so do not use them there.

## `transform`

`transform` in `+droplet.server.ts` rewrites the droplet's HTML on every
request, prerendered or live, with the request's event. What a build-time
render cannot know goes here:

```ts
import type { TransformEvent } from "$droplets/server";

const escapeHtml = (text: string) =>
  text.replace(/[&<>"']/g, (c) => `&#${c.charCodeAt(0)};`);

export const transform = ({ html, host }: TransformEvent) =>
  html.replaceAll("@HOST@", () => escapeHtml(host.host));
```

`transform` writes into HTML, and `host` comes from the request: escape what
you splice in, and pass the replacement as a function, so `$&` or `$'` in
it is not read as a pattern. A list of functions runs in order.

`error()` and `redirect()` stop it as they stop a load: the fragment answers
with that status, or the redirect. `transform` runs on fragments only;
`_data` answers what the load returned. The
[shop demo](/integrate/hosts/shop-demo/#stale-free-ssg-with-a-version-prop)
redirects an old link from its `transform`.
